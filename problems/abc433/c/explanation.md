# abc433 c 解説まとめ

## 問題概要 (1122 String)
数字だけからなる文字列 $T$ が「1122文字列」であるとは、次をすべて満たすこと。

1. $T$ は空でない数字列
2. $|T|$ は偶数
3. $T$ の前半($1$〜$|T|/2$文字目)はすべて同じ数字
4. $T$ の後半($|T|/2+1$〜$|T|$文字目)はすべて同じ数字
5. 前半の数字に $1$ を足すと後半の数字になる(例: 前半が`4`なら後半は`5`)

与えられた数字列 $S$($1 \le |S| \le 10^6$)の**部分文字列**のうち、1122文字列であるものの
個数を数える(同じ内容でも取り出す位置が違えば別カウント)。

例: `1122`,`01`,`444555` はOK。`1222`(前半が同じ数字でない),`90`(差が1でない) はNG。

サンプル `1112222334445556555` → 答え `11`。

## 公式解説のアプローチ
ポイントは「**境界(隣り合う2文字が異なる数字になっている位置)に注目する**」こと。

1122文字列は必ず「前半が数字 $d$ の連続、後半が数字 $d+1$ の連続」という形をしているので、
文字列を**連続する同じ数字のかたまり(run)** に分解しておくと考えやすい。
例えば `1112222334445556555` は

```
(1,3) (2,4) (3,2) (4,3) (5,3) (6,1) (5,3)
```

のように「数字, 連続個数」のペア列(ランレングス圧縮)に分解できる。

隣り合う2つのかたまり $(d_i, c_i)$ と $(d_{i+1}, c_{i+1})$ について、
$d_{i+1} = d_i + 1$ が成り立つ境界だけが1122文字列の候補になる。
その境界では、前半に使う個数 $k$($1 \le k \le c_i$)と後半に使う個数 $k$
($1 \le k \le c_{i+1}$、**前半と後半は同じ長さ**でなければならない)を自由に選べるので、
作れる1122文字列の個数はちょうど $\min(c_i, c_{i+1})$ 通りになる。

これを全ての境界について足し合わせれば答えが求まる。

サンプルでの内訳:
- `(1,3)-(2,4)`: $\min(3,4)=3$
- `(2,4)-(3,2)`: $\min(4,2)=2$
- `(3,2)-(4,3)`: $\min(2,3)=2$
- `(4,3)-(5,3)`: $\min(3,3)=3$
- `(5,3)-(6,1)`: $\min(3,1)=1$
- `(6,1)-(5,3)`: $6+1=7\ne5$ なので $0$

合計 $3+2+2+3+1+0=11$ でサンプルと一致する。

### 実装方針1: ランレングス圧縮
$S$ を先頭から走査して `(数字, 連続個数)` の列を作り(`itertools.groupby` 相当)、
隣り合う要素同士を上のルールでチェックする。列の長さは $S$ の文字数以下なので $O(N)$。

### 実装方針2: 境界から左右に伸ばす(直接計算)
ランレングス配列を作らずに、`S[i] + 1 == S[i+1]` となる境界 $i$ を見つけたら、
そこから **左に同じ数字が何個連続しているか**(=$c_i$)、**右に同じ数字が何個連続しているか**
(=$c_{i+1}$)をその場で数えて $\min(c_i, c_{i+1})$ を加算する。
一見 二重ループに見えるが、それぞれの run は高々2つの境界(自分の左隣・右隣)からしか
参照されないため、全体では各文字が定数回しか見られず $O(N)$ になる。

どちらの方法でも計算量は $O(N)$。

## `main.cpp` がTLE/WAになった理由
今の実装は「全ての中心位置 $i$」から `idx_front`/`idx_back` を1文字ずつ外側に広げながら、
その都度 `substr` で切り出した文字列に対して `check()`(前半・後半が同じ数字か、`stoi` で
差が1かを判定)を呼んでいる。

- **計算量が $O(N^2)$ 以上になっている**: たとえば `S` が同じ数字の連続(例:`111...1`)
  だった場合、`front`・`back` はどれだけ広げても「前半が同じ数字・後半が同じ数字」
  という条件だけは常に満たしてしまうため、ループが最後まで止まらない。
  中心位置ごとに $O(N)$、それが $N$ 箇所あるので最悪 $O(N^2)$ で、$N=10^6$ では到底間に合わない
  (`check()` 内の `substr`/`all_of` のコストも含めるとさらに重い)。
- **`stoi` は `int` の範囲しか扱えない**: `front`/`back` が10桁を超える数字列になると
  `std::stoi` は `std::out_of_range` を投げる(桁数が大きい入力ではほぼ確実に発生する)。
  数値に変換して引き算する必要はなく、「同じ数字が続いているか」と「境界の2数字の差が1か」
  さえ分かればよいので、そもそも `stoi` で数値化する設計自体が不要かつ危険。

## 直すべき方針
1. 数値変換(`stoi`)はやめて、文字列を先頭から1回走査し `(数字, 連続個数)` のランレングス列を作る。
2. 隣り合うペアについて「後ろの数字 = 前の数字 + 1」なら `min(左の個数, 右の個数)` を答えに加算する。
3. これで一切のバックトラック無しに $O(N)$ で解ける。

## まとめ
- 「前半が同じ数字・後半が同じ数字」という条件は、文字列をランレングス圧縮すれば
  自然に扱える(連続する同じ文字の塊をひとまとまりとして扱う典型パターン)。
- 「境界をまたぐ2つの塊の個数の $\min$ を足し合わせる」という数え方が今回の核心。
- 数値化して差を取るのではなく、文字(digit)同士の比較で済ませることで
  桁あふれや `stoi` の範囲外エラーを避けられる。
